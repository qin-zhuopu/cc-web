# 产品简报：SK · 共享内核 (Shared Kernel)

> 本文档是 CodePilot Web 六边形重构中 **SK · Shared Kernel** 限界上下文的产品简报。
> 架构基线见 [../../architecture/hexagonal-decomposition.md](../../architecture/hexagonal-decomposition.md)，边界契约见 [../../architecture/context-boundaries.md](../../architecture/context-boundaries.md)。
> 技术实现见 [architecture.md](./architecture.md)。

## 执行摘要

共享内核是 CodePilot Web 六边形架构的**最底层地基**。它不属于任何业务领域——它不知道"会话""消息""Provider"是什么——但它提供了所有 10 个业务上下文都要反复用到的一组横切能力：结构化错误分类、平台检测、敏感信息脱敏、i18n 翻译端口、运行时日志环形缓冲、时钟与 ID 生成。

在现有 Electron 版 CodePilot 中，这些能力散落在 `error-classifier`、`platform`、`runtime-log` 等模块里，彼此耦合、被业务代码直接 `import` 具体实现，难以在纯逻辑核心中复用。重构的目标是把它们收敛成一个**零框架、零业务依赖**的共享内核包 `packages/core/shared-kernel/`，以稳定的端口接口对外暴露，让上层每个上下文都通过依赖倒置消费它，而非依赖某个具体实现。

为什么是现在：绞杀者迁移顺序把 SK 排在第一位。它没有任何上游依赖，blast radius 为零，是验证六边形分层铁律（依赖方向永远指向核心）的最安全起点。SK 的接口一旦钉死，后续 10 个上下文才能安全地在其之上生长。

## 问题陈述

现有 CodePilot 代码库中，横切关注点存在三类结构性问题：

1. **错误语义不统一。** 错误分类逻辑（16 类结构化错误）与调用方混在一起，不同 Runtime / Provider 对"同一种错误"的表达不一致，UI 拿到的错误信息时而是原始异常时而是分类结果，用户看到的错误提示语义漂移。
2. **敏感信息泄漏风险。** 日志、错误上报、运行时缓冲区里可能夹带 API Key、token、路径等敏感数据。脱敏逻辑若不集中在一处，任何新增日志点都是潜在泄漏点。
3. **横切能力被直接耦合。** 平台检测、时钟、ID 生成、i18n 翻译这些能力被业务代码直接 `import` 具体实现，导致核心逻辑无法脱离框架/环境做纯逻辑测试，也无法在测试中替换（比如冻结时钟、确定性 ID）。

这些问题在 Electron 单体里靠"约定"勉强维持，但重构成六边形后，`packages/core` 里禁止出现对具体实现的 import——若没有一个干净的共享内核先把这些能力抽象成端口，上层上下文根本无法遵守分层铁律。

## 解决方案

构建 `packages/core/shared-kernel/`，一个**纯 TypeScript、零框架依赖**的核心包，对外提供 7 个稳定端口：

- **ErrorClassifier** — 把任意底层异常映射为 16 类结构化错误之一，携带稳定的错误码、可翻译的消息键、是否可重试等元信息。
- **Platform** — 只读的平台检测（OS、架构、运行环境），供上层做条件分支而无需自己探测。
- **Redactor** — 对任意字符串/结构做敏感信息脱敏，集中管理脱敏规则，任何日志/上报点都经它过滤。
- **TranslationPort** — i18n 翻译端口，按消息键 + 语言返回文案；SK 只定义端口与内建 key 契约，具体文案表由适配器提供。
- **RuntimeLog** — 有界环形缓冲的运行时日志，供诊断/导出，写入自动经 Redactor 脱敏。
- **Clock** — 时间源抽象，生产用系统时钟，测试可注入冻结时钟。
- **IdGenerator** — ID 生成抽象，生产用真实随机源，测试可注入确定性序列。

所有端口都是接口定义在核心内、实现在适配器层（NestJS 侧或纯函数适配器），通过依赖倒置注入。业务上下文只依赖端口签名，永不依赖实现。

## 差异化定位

SK 不是一个"工具库"，它是一个**契约层**。它的价值不在于代码量，而在于：

- **语义一致性契约。** 错误分类的 16 类、脱敏规则、翻译键都是全局单一事实来源。任何上下文对同一错误的表达必然一致——这直接支撑了 CLAUDE.md「语义验收与反假数据」要求的"跨 Runtime / Provider 一致"。
- **可测试性地基。** Clock / IdGenerator 的端口化让上层用例可以做确定性单元测试，无需 mock 框架或真实时间。
- **零依赖倒逼纯净。** SK 依赖端口为"无"，它是唯一一个可以被所有人依赖而不产生循环的上下文，天然充当分层铁律的守门人。

诚实地讲，SK 没有炫技的技术护城河——它的护城河是**边界纪律**：只要它保持零业务依赖、接口稳定，整个重构的依赖图就不会腐坏。

## 服务对象

SK 没有终端用户，它的"用户"是**其余 10 个限界上下文及其开发者**：

- **C1–C10 的核心用例代码** — 消费 Clock/IdGenerator 做实体创建、消费 ErrorClassifier 统一错误、消费 TranslationPort 出可读文案。
- **适配器层开发者** — 实现 SK 端口的具体适配器（系统时钟、真实脱敏规则表、i18n 文案表）。
- **诊断与运维场景** — 通过 RuntimeLog 环形缓冲导出脱敏后的运行时日志排障。

成功对这些"用户"意味着：他们能只依赖 SK 的端口签名写纯逻辑，测试可注入替身，永不为横切能力操心具体实现。

## 成功标准

- `packages/core/shared-kernel/` 中不出现任何框架 / 第三方具体实现 import（`better-sqlite3`、`anthropic`、`@nestjs/*` 等一律为零）。
- 7 个端口接口全部定义完成，且被至少一个上层上下文（试点 C7）实际消费验证。
- 16 类结构化错误全部有稳定错误码 + 可翻译消息键；同一底层异常在任意上下文分类结果一致（反例 smoke 可断言）。
- Redactor 覆盖已知敏感模式（API Key、token、绝对路径、邮箱等），RuntimeLog 写入默认经脱敏。
- Clock / IdGenerator 在测试环境可注入确定性替身，支撑上层用例的确定性测试。

## 范围

**第一版包含（In）：**
- 7 个端口的接口定义（TypeScript interface / type）。
- 16 类结构化错误的枚举、错误码、消息键契约。
- ErrorClassifier 的分类规则契约（输入异常 → 分类结果的映射语义）。
- Redactor 的脱敏规则契约与内建规则集。
- TranslationPort 端口 + 内建消息键清单（SK 自身产生的 key）。
- RuntimeLog 环形缓冲的容量/淘汰语义契约。
- Clock / IdGenerator 端口契约。

**明确排除（Out）：**
- 任何业务领域概念（会话、消息、Provider、Runtime 等——属 C1–C10）。
- i18n 具体文案表的内容（由适配器/各上下文提供各自的 key，SK 只定义端口与自身 key）。
- 持久化（SK 不落库；RuntimeLog 是内存环形缓冲）。
- 具体适配器实现细节（系统时钟实现、真实随机 ID 算法选型等在适配器层，architecture.md 给签名不给实现）。

## 愿景

如果 SK 做对了，它应该在整个重构生命周期里**几乎不变**——这正是共享内核的理想终态：一个稳定、被所有人信赖、无需频繁改动的地基。它成为团队讨论"这个错误该归哪一类""这个字段该不该脱敏""这个文案键在哪定义"的单一权威。长期看，SK 的端口契约稳定度就是整个六边形架构健康度的晴雨表——SK 频繁改动，意味着边界划错了；SK 长期静默，意味着地基牢固。
