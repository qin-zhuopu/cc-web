# 04 · 踩坑与根治

本轮踩的所有坑与处置。给接续者：这些坑会再遇到。

## 坑 1：项目原本没有独立 git 仓库（已根治）

- **现象**：会话开始 `git status` 显示 clean，但我们新建了大量文件。`git add package.json` 报 `repo` 被忽略。
- **根因**：`codepilot-web/` 下**没有独立 `.git`**。唯一 git 仓库是上层 dotfiles 仓库 `C:/home/14409.JEREH`，其 `.gitignore` 第 55 行 `/repo/` 把整个 repo 子树（含本项目）忽略。所以项目层面等于没有版本控制。
- **根治**：在 `codepilot-web/` 里 `git init` 建独立仓库（提交 `681e37b` 起）。**勿把项目提交进 dotfiles 仓库**。

## 坑 2：CRLF 误报让脏检查永远失败（已根治，关键）

- **现象**：`run-dev-auto.sh` 脏检查第一次跑时，`git status` 报几百个 `.claude/skills/**`、`_bmad/**` 文件为 ` M`（已修改），但 `git diff` 实为 0 改动。
- **根因**：`core.autocrlf=true` 且**无 `.gitattributes`**，git 索引存 CRLF、工作区是 LF，导致 status 把纯行尾差异误报为改动。
- **影响**：这个不修，无人值守链路根本起不来——脏检查会永远失败。
- **根治**：加 `.gitattributes`（`* text=auto eol=lf` + 二进制类型 binary）+ `git add --renormalize .` 规范化索引（提交 `fffc60f`）。

## 坑 3：退休模型让 claude -p 空转（导致 run-dev-auto.sh 废弃）

- **现象**：`run-dev-auto.sh` 跑起来后 `claude -p` 子进程反复重启却产不出任何东西，输出只有一行「Claude Opus 4 was retired on June 15, 2026」。
- **根因**：环境变量 `ANTHROPIC_MODEL=kr/claude-opus-4.8`（已退休），`claude -p` 子进程继承它、撞退休错误空转。
- **处置**：放弃 CLI 编排，改用 **Workflow**——其子代理继承会话模型，不碰 CLI 子进程，绕开退休模型。
- **用户后来给的正确配置**（写进 `apps/api/.env`，gitignored 不入库）：`ANTHROPIC_MODEL=Jereh-Kimi-K2.6`、`ANTHROPIC_BASE_URL=https://litellm.jereh.cn`、`CLAUDE_CODE_SUBAGENT_MODEL=Jereh-Kimi-K2.6` 等 + `ANTHROPIC_AUTH_TOKEN`（密钥，只写 .env、绝不回显/入库）。此配置供 C2 SDK query 与 E2E 测试**运行时**读取，**不能注入 workflow 子代理**（子代理继承会话模型，由会话启动时的 env 决定，改不了在跑的会话）。

## 坑 4：Git-Bash 下 git/find 输出异常（全程规避）

- **现象**：裸 `git status --short` 返回伪造/固定文案；`find -newermt` 无输出；`find` 有时被 Windows find 拦截报「Parameter format not correct」。
- **规避**：统一用 `/mingw64/bin/git` 全路径直调；枚举文件用 Glob 工具或 `ls -R`，不依赖裸 `git status`/`find`。（CLAUDE.md 已记此约定。）

## 坑 5：网络抖动导致 workflow 卡死 / 子代理 stream timeout（已处置）

- **C2-E2 卡死**：哨兵对比两个周期发现 HEAD/改动数/进程/文件全部零变化，读 journal 见**同一 agent key 反复 started 无 result**（API 反复重试死掉）→ `TaskStop` 停掉 → `Workflow({resumeFromRunId})` 续跑（已完成 agent 从缓存秒回，卡住的重跑）→ 恢复成功。
- **拆分子代理 stream timeout**：C2-E3 拆分子代理报「API Error: Stream idle timeout」中途死→重派一次成功。
- **判据**：卡死 = 同一 key 反复重试 + 文件时间戳冻结 + result 数不增。正常推进 = 不同 key 前进 + 新文件落盘 + result 数增长。

## 坑 6：workflow 脚本内嵌反引号冲突（已处置）

- **现象**：C1-E2 workflow 首次启动报 `Script parse error: Unexpected token`——mergeReport 提示里内嵌了带反引号的 markdown 代码（`` `export type...` ``），与外层模板字符串反引号冲突。
- **处置**：把内嵌反引号改成普通引号描述。**教训**：workflow 脚本（JS 模板字符串）里的 agent prompt 不要写内嵌反引号代码块。

## 坑 7：JSDoc 注释里的 */ 提前闭合块注释（workflow 内部自修多次）

- **现象**：多个 epic 的 merge 阶段首轮 typecheck 崩溃，因源码 JSDoc 里字面量 `permission_*/rate_limit`、`cache*/totalTokens` 的 `*/` 提前闭合了 `/**` 块，后续注释被当代码解析爆几十处语法错。
- **处置**：workflow 的 merge agent 自己发现并改写（拆开 `*` 与 `/`）。**教训**：注释里避免连写 `*/`。

## 坑 8：我的输出退化（诚实记录，未根治）

- **现象**：多轮在工具调用之间夹带大段重复字符（"course"、"." 等），偶尔导致漏步——C2-E1 曾漏启动 workflow、C2-E3 差点漏提交。
- **兜底**：**每步幂等自检**（先查 HEAD/文件状态再决定动作，如「若 HEAD 仍是上一个 epic 则执行提交」），+ 哨兵每 20 分钟守断点。靠这两条，退化没有损坏已交付成果。
- **给接续者**：这是我这次的生成稳定性问题。接续时若同样退化，坚持幂等自检模式——不依赖连续输出，每个关键动作都用命令验证前置状态。
