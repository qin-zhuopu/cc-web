# 06 · 工作流机制与哨兵

无人值守能扛住整夜的三个机制：workflow 编排、每步幂等自检、哨兵 cron。

## workflow 脚本模式（每 epic 一个 wf-*.mjs）

产物在 `_bmad-output/implementation-artifacts/wf-<epic>.mjs`，已入库。范式：

```
export const meta = { name, description, phases: [...] }
const RULES = `<注入每个 agent 的公共铁律：核心包禁用清单、verbatimModuleSyntax、
                术语纪律、"不要改 index.ts"、"不要跑 npm run test"、目录约定、现状复用>`
phase('波次1'); const w1 = await parallel([ ()=>agent(prompt, {label, phase}), ... ])  // 无依赖并行
phase('波次2'); ...                                                                    // 依赖前波次
phase('Merge+Verify'); const merge = await agent(<合并 index.ts + 跑 npm run test 自修到绿>)
phase('Review');       const review = await agent(<对抗评审，逐条判定真缺陷/nitpick>)
return { ..., merge, review }
```

**关键约束**（踩坑得出）：
- agent prompt 里**不要写内嵌反引号代码块**（与外层模板字符串冲突，见 04 坑 6）。改用普通引号描述或缩进。
- 有依赖链的故事**串行 await**（都改同一文件时必须串行避免冲突）；无依赖的**parallel 并行**。
- index.ts 桶文件**只在 Merge 阶段统一改**（并行 agent 同改会冲突）。
- 每个 agent 是全新上下文，公共铁律必须在 prompt 里重述。

## 每个 epic 完成后我在会话里做（不放进 workflow，保持人类控制）

1. **独立复跑 `npm run test`** 验证（不轻信 workflow 汇报的绿）。因终端输出偶被吞，用 `npm run test > /tmp/x.log 2>&1; grep -E "Test Files|Tests |check-core-imports" /tmp/x.log`。
2. 审读对抗评审结论，**亲自裁决**：真缺陷（阻断/中等）当轮修 + 补测试；nitpick/超范围记 `deferred-work.md`。修完再复跑门禁。
3. 更新 `sprint-status.yaml`：epic 与其所有故事标 done。
4. **git 提交断点**（一 epic 一 commit，Co-Authored-By 规范，用 `/mingw64/bin/git`）。

## 每步幂等自检（对抗我的输出退化）

因我多轮输出退化（见 04 坑 8），关键动作都**先查前置状态再决定**，不依赖连续输出：
- 提交前：`git log --oneline -1` 看 HEAD 是否还是上一个 epic → 是则执行提交，否则说明已提交。
- 启动 workflow 前：`ls epic-<x>/` 确认 stories 存在、`git log` 确认 HEAD。
- 这样即使某轮输出退化漏了步骤，下一轮自检能发现并补。C2-E3 差点漏提交就是靠这个补回的。

## 哨兵 cron（防卡死/网络抖动）

用 CronCreate 建了 session-only 哨兵（job `080306b0`，每 20 分钟 :13/:33/:53 触发）。每次做：
1. `git log -1` + `git status --porcelain | wc -l` 看 HEAD 和改动数。
2. `ps -W | grep -ci claude.exe` 看进程。
3. 读 workflow journal.jsonl 尾部判断：**卡死 = 同一 agent key 反复 started 无 result + 文件时间戳冻结 + result 数不增**；**正常 = 不同 key 前进 + 新文件落盘 + result 增长**。
4. 卡死则 `TaskStop` + `Workflow({resumeFromRunId})` 续跑（已完成 agent 从缓存秒回）；正常则不打断、记一句进度。

**哨兵实战战果**：
- 识别并恢复了 C2-E2 卡死（同一 key 4 次 started 无 result → stop+resume 成功）。
- 多次确认「已停在干净断点等用户」的状态无异常。

## workflow 续跑（resumeFromRunId）

`Workflow({scriptPath, resumeFromRunId})`：相同 (prompt, opts) 的 agent 从缓存返回，改过/新的重跑。用于卡死恢复、脚本迭代。journal.jsonl 记每个 agent 的 started/result，是判断卡死 vs 推进的权威依据。
