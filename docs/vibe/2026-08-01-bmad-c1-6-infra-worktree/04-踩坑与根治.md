# 04 · 踩坑与根治

本轮踩了五个真实的坑，全部定位根因并根治，没有一个是靠反复试错蒙过去的。

## 坑 1：worktree 缺 devDependencies（tsc/vitest not found）

- **现象**：worktree 里跑 `npm run lint` 报 `'tsc' is not recognized`；查 node_modules 无 typescript / vitest。
- **误区排除**：先试了 `npx tsc`（装到无关老包 tsc@2.0.4）、`node node_modules/typescript/bin/tsc`（路径不存在），都不对。
- **根因**：git worktree 不复制 node_modules；我此前只在 worktree 跑了 `npm install better-sqlite3`（单包），根 devDependencies 从没装进这个 worktree。
- **根治**：在 worktree 跑一次完整 `npm install`，tsc/vitest 补齐。

## 坑 2：core 的 exports 指向源码，node dist 起服务 ERR_MODULE_NOT_FOUND

- **现象**：`node apps/api/dist/main.js` 报 `Cannot find module '.../packages/core/src/domain/error/error-code.js'`。
- **根因**：`packages/core/package.json` 的 main/exports 指向**源码** `./src/index.ts`，而非编译产物 dist。测试能过是因 vitest 用 esbuild 实时转译 .ts；但纯 node 运行会按 exports 加载 src/index.ts，再顺着里面的 `./xxx.js` 相对导入找编译产物却找不到（源码目录没有 .js）。
- **为何现在才暴露**：apps/api 的 main.ts 之前一直是占位符（API_PLACEHOLDER），从没 bootstrap 过。我是第一个真正 `node dist` 起服务的人。这是**既有配置问题**，不是本 epic 引入的。
- **处置**：这属于计划外、触及 core 包配置的决策，用 AskUserQuestion 让用户拍板 → 用户选「修 core exports 指向 dist」。改为 `main: ./dist/index.js` + `exports: { ".": { types: ./dist/index.d.ts, import: ./dist/index.js } }`，重编译后 dist 齐全。

## 坑 3：NestFactory 缺 HTTP 驱动

- **现象**：服务启动报 `No driver (HTTP) has been selected... install @nestjs/platform-express`。
- **根因**：apps/api 只装了 @nestjs/common + @nestjs/core，没装 platform-express。同样因为从没真正 bootstrap 过 HTTP 服务，此前无从暴露。
- **根治**：`npm i @nestjs/platform-express@10.4.15`（pin 版本对齐既有 @nestjs 版本）。这是本 epic 引入 HTTP 入口的合理运行时依赖。

## 坑 4：DB 文件被占，rm 失败

- **现象**：curl smoke 后 `rm smoke.db` 报 `Device or resource busy`；TaskStop 报 no task found（后台 shell 已脱离）。
- **根治**：用 PowerShell `Get-CimInstance Win32_Process` 按命令行匹配到 node 进程（pid 29148）Stop-Process 强杀，再删 WAL 相关的三个文件（.db / .db-shm / .db-wal）。

## 坑 5：master 期间分叉，fast-forward 失败

- **现象**：准备合并时发现 master 已从 dbb77d3 前进到 087af84（c2-4 期间被提交进来了），epic-c1-6 与 master 分叉，ff 不可能。
- **分析**：手动比对两提交文件清单，**唯一重叠是 sprint-status.yaml**（c2-4 标 c2-4-* done、c1-6 标 c1-6-* done），其余零重叠。
- **根治**：用户选普通 merge（--no-ff）。实际合并**零冲突**——因两边改的是 sprint-status.yaml 不同行区块，git 按行三方合并自动处理，两边 done 标记都保留。

## 共同教训

三个坑（1/2/3）本质同源：**c1-6 是第一个真正把服务 `node dist` 跑起来的 epic**，之前所有 epic 都停在纯逻辑/测试层（vitest 转译 .ts、apps/api 是占位入口）。所以一批「打包/运行时配置」问题被同时首次暴露——它们不是 c1-6 的 bug，是整个项目从「能测」迈向「能跑」时必然要补的一课。
