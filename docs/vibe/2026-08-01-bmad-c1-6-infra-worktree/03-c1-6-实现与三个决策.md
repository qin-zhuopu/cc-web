# 03 · c1-6 实现与三个决策

## 调研：c1-6 无现成 spec，先摸清范围

与 c2-4 不同，c1-6 **没有 SPEC.md / stories.yaml**，只有 sprint-status 里 4 个故事 id。开工前用 3 个并行 Explore agent 摸清：C1 四个用例的构造签名、桶导出、SK 适配器范式、DI 测试范式、import 守卫边界、tsconfig、SQLite/schema 现状、TitleGeneratorPort 悬空情况。

关键调研结论：
- **桶导出就绪**：4 个用例 service 是**值导出**（可从 @codepilot/core 直接 import），端口/领域类型是类型导出（import type）。
- **import 守卫只扫 `packages/core/src`**：better-sqlite3 / @nestjs 放 apps/api 完全合规。
- **DI 测试范式**：沿用 shared-kernel.module.spec.ts 的 `NestFactory.createApplicationContext`（@nestjs/testing 没装）。
- **一个真实悬空依赖**：SetSessionTitleService 依赖 TitleGeneratorPort，但其实现方在 C2（GenerateTitleService，排在 c2-7 还没做），apps/api 里连 AgentRuntimeModule 都不存在。

## 三个拍板决策（AskUserQuestion）

1. **TitleGeneratorPort 悬空怎么处理** → **占位 stub 适配器**：写 StubTitleGenerator（generateTitle 抛错，触发 SetSessionTitleService 的 catch→记 warn→保留原标题降级路径），C2 落地后替换。
2. **范围做到哪层** → **全部 4 个故事**（含控制器 + 真 NestFactory bootstrap，能 curl 打通）。
3. **建表 schema** → **只建 C1 本体列**，时间用 INTEGER 存 epoch 毫秒（对齐 SK.Clock），C2/C7/C5 寄存列各自 epic 用 ALTER TABLE 补（字段归属铁律）。

## 领域字段（建表依据）

- **ChatSession 10 本体字段**：id / title / titleOrigin / status(active|archived) / mode(code|plan|ask) / source(user|task) / workingDirectory / projectName / createdAt(number) / updatedAt(number)。
- **Message**：id / sessionId(FK) / role(user|assistant) / content(经 encode/decodeContent JSON) / createdAt(number) / streamStatus / tokenUsage?(无值不落假0) / isHeartbeatAck / taskRunId?。
- 值得注意：TitleOrigin / StreamStatus / MessageRole 都是**字符串字面量联合**（非 enum），直存直读。

## 实现产出（apps/api，17 文件）

### 步骤 0：DB 连接层（apps/api/src/database/）
- `database.tokens.ts` —— `DATABASE = Symbol('DATABASE')`（对齐 sk-tokens 约定）。
- `init-db.ts` —— 建表 DDL：chat_sessions（10 本体列）+ messages（FK ON DELETE CASCADE，content/token_usage 为 TEXT 存 JSON，is_heartbeat_ack 用 INTEGER 0/1）；`PRAGMA journal_mode=WAL` + `foreign_keys=ON`（级联生效必须显式开）；idx_messages_session 索引。
- `database.module.ts` —— `forRoot(dbPath)` 用 useFactory 建连接+建表，global module，支持 `:memory:`（测试）与文件路径（默认 CODEPILOT_DB_PATH 或 codepilot.db）。

### 步骤 1（c1-6-3）：两个 SQLite 仓储
- `sqlite-session-repository.ts` —— implements SessionRepository。行↔实体编解码，`listAll()` 不 filter/sort/limit（权威在用例层），缺失 id 靠 UPDATE/DELETE 影响 0 行天然幂等 no-op，save 用 `ON CONFLICT DO UPDATE` upsert。
- `sqlite-message-repository.ts` —— implements MessageRepository。content 经 encode/decodeContent，token_usage NULL→undefined（不落假 0），rowid 游标分页（beforeRowId），deleteBySession 返回 changes。

### 步骤 2（c1-6-1）：ConversationModule + stub
- `conversation.tokens.ts` —— 7 个 Symbol token（2 仓储 + 4 用例 + 1 TitleGenerator）。
- `stub-title-generator.ts` —— StubTitleGenerator（抛错触发降级，注释标明 c2-7 替换）。
- `conversation.module.ts` —— imports SharedKernelModule；仓储 useFactory inject DATABASE；**4 个用例 useFactory 严格按各自构造签名 inject 对应 token**（AppendMessageService 的 messages 参数在前，是易错点）；**exports 只含 4 个用例 token，不导出仓储写端口**（c1-6-4 契约）。

### 步骤 3（c1-6-2）：控制器 + bootstrap
- `session.controller.ts` / `message.controller.ts` —— REST，只 @Inject 用例 token 不碰仓储，注释标「无鉴权勿暴露公网」。
- `app.module.ts` —— 聚合 DatabaseModule.forRoot() + SharedKernelModule + ConversationModule。
- `main.ts` —— 换掉占位符 `API_PLACEHOLDER`，改真 `NestFactory.create(AppModule)` + listen（默认 127.0.0.1:3001）。

### 步骤 4（c1-6-4）：消费方契约测试
- `conversation.module.spec.ts` —— 5 个测试：4 用例 token 解析、会话往返、消息追加→历史、级联删除、**消费方契约**（从下游 Module 视角验证仓储写端口 token 不可解析）。第一版契约测试是空转断言，我主动改实成「下游只 import ConversationModule 时用例可达、仓储 token strict 解析抛错」。

## DI 接线范式要点

核心包零框架 → 用例 service 无 @Injectable，靠 ConversationModule 的 useFactory 手工注入构造依赖。interface 运行时被擦除，必须用 Symbol token 作注入标识。所有相对 import 带 `.js`（NodeNext），类型-only 用 import type（verbatimModuleSyntax）。
