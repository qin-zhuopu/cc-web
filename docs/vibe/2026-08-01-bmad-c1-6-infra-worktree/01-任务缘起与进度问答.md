## 追问一：C1 为啥 5/6 就跳去做 C2？

用户看到「C1 5/6 done」问为什么没做完就做后面。核心解释：

**这不是跳着做，是按「层」切而非按「领域边界」切。** C1 的 6 个 epic 分两层：
- c1-1~5 是**纯核心层**（领域模型、用例、端口接口），零框架、可纯单测、无人值守能跑。
- c1-6 是**基础设施层**（NestJS DI + SQLite 仓储 + HTTP 控制器），要接真框架真数据库，必须人在场验证。

整夜无人值守执行**故意把所有基础设施层（c1-6、c2-6、c2-7、epic-accept）攒到最后**。原因：① 无人值守跑不了基础设施层（要接 SQLite/litellm/SSE，机器自己没法确认对错）；② 依赖方向允许——C2 核心依赖的是 C1 的**用例接口**（GetSessionHistoryUseCase / AppendMessageUseCase），这些在 c1-1~5 已定义，c1-6 只是给接口接上真实现，C2 核心 import 的是接口（import type），不碰 c1-6 实现。

## 追问二：SQLite 装了没？DI 是啥？

- **SQLite**：我扫了三个 package.json + node_modules，确认**没装** better-sqlite3。架构文档提到的「现有 chat_sessions 表」只存在于被参考的外部项目 CodePilot，不在本仓库。import 守卫禁止核心包 import better-sqlite3，所以它只能待在 apps/api。
- **DI（依赖注入）**：用 StartStreamService 的构造函数举例——用例只声明要接口（AgentRuntimePort / GetSessionHistoryUseCase），自己不 new；由 NestJS Module 登记「token → 实现」的绑定表，容器把真实现注入进构造函数。c1-6 = 装 SQLite + 写真仓储 + NestJS DI 接线，三件事是同一层的同一件事。

## 追问三：「安装啊，为啥不装呢」→ 开 worktree 做 c1-6

用户想直接装 SQLite。我说明「装 better-sqlite3 实质等于开工 c1-6」（单装无意义会成死依赖、是原生模块 Windows 要编译、工作区还挂着 c2-4 未入库），并给了三个选项。用户选择：**开 worktree 正式做 c1-6，完事合并回来**。

这既能正式推进 c1-6，又把 c1-6 与 master 工作区那批 c2-4 未跟踪文件天然隔离开。
