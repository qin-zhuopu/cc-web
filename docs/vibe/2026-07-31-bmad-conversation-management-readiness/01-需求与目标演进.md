# 01 · 需求与目标演进

## 起点

用户执行 `/bmad-help` 并附带「看下当前进度」。我解析了 `_bmad/_config/bmad-help.csv` 和合并配置，发现 codepilot-web 的 BMad 标准产出目录（`_bmad-output/planning-artifacts`、`implementation-artifacts`）以及 `docs/{architecture,bmad-progress,contexts}` **看似为空**。基于此我最初汇报「BMad 工作流尚未起步」——这个初判后来被证明是错的（见 03 文档）。

## 用户口述需求（原文要点）

> 我要先做个 nestjs 的后端，让这个后端能提供接口，能让用户新建个会话，然后能返回 claude agent sdk 的所有的响应。用户能列出所有历史会话和活跃会话。活跃会话能接着聊。历史会话也能继续聊。也就是关于整个会话的管理，都要是完整的。整体参考 /c/home/14409.JEREH/repo/github.com/op7418/CodePilot

## 需求四要点拆解

| 要点 | 含义 |
|---|---|
| 新建会话 | 提供接口创建一个新的会话 |
| 流式返回 SDK 所有响应 | 把 Claude Agent SDK 的完整消息流（文本/思考/工具调用/工具结果/系统事件/result）返回给客户端 |
| 列出历史 + 活跃会话 | 两个列表：全部历史会话、当前活跃会话 |
| 活跃与历史都能接着聊 | 都能在已有会话上继续对话（靠 SDK resume 续接上下文） |

## 目标形态演进

1. 最初我用原生 plan mode 写了一份「精简 TypeScript 单体后端」方案（TypeORM 单体、SSE），并 ExitPlanMode 请求批准。
2. 用户**打断并否决**：「走 bmm 方法论啊」——要求改走 BMad（bmm）方法论，不用原生 plan。
3. 我据此询问 BMad 入口，用户最终选择「完整规划（PRD 起步）」。
4. 但随后发现之前已经做过完整 BMad 规划（见 03、04），于是不需要重写 PRD，直接进入就绪度校验。

## 各次 AskUserQuestion 确认的关键选项

在原生 plan 阶段（后被 BMad 流程取代，但决策仍有参考价值）确认过：
- **持久化**：TypeORM + SQLite
- **流式传输**：SSE
- **SDK 能力范围**：完整消息流（透传 text/thinking/tool_use/tool_result/system/result，不含 MCP/权限交互）
- **活跃 vs 历史**：按是否正在流式响应区分（活跃 = 当前有一个 SDK query 正在流式；历史 = 已落库、无进行中流）

在 BMad 流程阶段确认过：
- **BMad 入口**：完整规划（PRD 起步）→ 但因文档已存在，实际转为直接校验
- **实施方向**：忠于文档全套走（六边形架构，而非我最初的精简单体）
- **Phase 4 入口**：先跑就绪度校验（bmad-check-implementation-readiness）

## 一个重要澄清：活跃/历史的定义与已有规划一致

用户选的「活跃 = 按是否正在流式响应」，和已有 C1/C2 规划里的定义**完全吻合**：
- C1（会话）持久层只有 `StreamStatus`（转录行生命周期：streaming/completed/interrupted/error），**不回答**「现在是否在流式」。
- C2（运行时）的 `StreamSession.phase`（active/settling/terminal）才是实时「是否在生成中」的唯一来源，且**绝不落库**。
- 规划特意强调：把持久 StreamStatus 当实时相位读，正是 stop/abort 卡死的根因，必须在类型层面切断。
