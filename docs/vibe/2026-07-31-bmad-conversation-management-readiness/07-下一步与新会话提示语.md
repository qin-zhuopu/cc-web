## 冲刺范围的决策时机（用户问过的问题）

用户问：「什么时候决定冲刺的范围？」

答：**不在就绪度校验这一步，而在下一步 `bmad-sprint-planning` 里**，由用户和我一起定。

```
[已完成] bmad-check-implementation-readiness  ← 只确认"文档够不够、能不能开工"，不定范围
      ↓
[下一步] bmad-sprint-planning                 ← 在这里决定冲刺范围，产出 sprint status
      ↓
       bmad-dev-story                         ← 按冲刺计划逐个故事开发
```

## 冲刺范围由什么决定（现都已就绪）

1. **史诗故事清单**：三份 epics-stories 已给出史诗划分（SK 4、C1 6、C2 7 史诗）和每份文末的 Sprint 建议分组。
2. **依赖顺序**：SK→C1→C2 的硬依赖决定哪些能进同一冲刺、哪些往后排。
3. **用户实施约束**：C2 本期只做 Claude SDK Runtime，把 S6.2/S6.3~6.5/6.7 移出本期。
4. **用户节奏偏好**（sprint-planning 里要问的）：一个冲刺吃多少、有无工时上限。用户倾向：**第一个冲刺先只做 SK 地基（E1 错误+类型、E2 Clock/IdGenerator/Platform）**。

文档里的「建议排期」是建议不是最终范围；真正拍板在 bmad-sprint-planning 并落成 sprint status 文件。
